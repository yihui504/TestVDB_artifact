## 四视角(每案逐一评估)
- **A 契约**:observed 是否明确违反包内契约断言?(判定断言文本是否真正覆盖观察到的行为面——机械包含性检查)
- **B 物理**:执行记录内部是否自洽?观察到的状态变化/复现声称是否有对应请求-响应记录支撑?
- **C 认知**:developer_cognition.json 的模式(by_design_patterns / blindspot_indicators / recurring_patterns / developer_cognition_signals)是否支持"该项目会将其认定为 bug"?若认知材料与该案行为面无关,记 NEUTRAL。
- **D 源码**:在**该案版本的源码 clone**中定位相关校验逻辑(grep 参数名/错误消息关键词/端点路由;可多次 grep 后 Read 命中文件),判定:validation_absent(文档/契约承诺的校验在源码中不存在)/ validation_present(校验在场且与观察一致→非缺陷证据)/ by_design_in_source(源码注释或结构表明行为有意为之)/ not_found(定位不到相关代码)。必须记录关键证据(文件:行号 + 一句话)。

## 聚合规则(保守,与既定口径一致)
- 终判 **CONFIRMED** 仅当:A 支持(或 A=NEUTRAL 但 B/C/D 至少两项明确支持)且 **D=validation_absent**,且无 by_design 证据;
- D=by_design_in_source,或 A 明确驳回,或 C 的 by_design_patterns 命中 → **FALSE_POSITIVE**;
- 其余(证据不足/定位不到/视角冲突)一律 **FALSE_POSITIVE**(保守方向:牺牲 recall 保 precision)。

## 纪律
- 只依据上述三类材料判定;不联网、不读材料清单之外的文件;每案独立,不受其他案影响。
- 源码 grep 失败(版本不匹配等)时如实记 D=not_found,不得臆测。
