# TITLE: `scroll` on a strict-mode collection ignores `max_query_limit` when `limit` is omitted


## Current Behavior

On a collection created with `strict_mode_config: {"enabled": true, "max_query_limit": 5}`:

- `scroll` with `limit=6` → 400 `Limit exceeded 6 > 5 for "limit"` ✓
- `scroll` with `limit=5` → 200, exactly 5 points ✓
- **`scroll` with `limit` omitted → 200 returning 10 points** (the built-in default of 10 exceeds the configured cap)

On the **same collection**, the `/points/query` endpoint with an omitted limit correctly returns 400 — there the default is materialized *before* the strict-mode check. In scroll, the raw `Option` is validated first (`check_limit_opt` requires both sides to be `Some`, so `None` passes) and the default is applied afterwards via `unwrap_or(default)` — so the omitted limit never meets the cap.

## Steps to Reproduce

Verified on **v1.19.0** (same on v1.18.0).

1. Create a strict-mode collection with `max_query_limit: 5` and seed 12 points:

```bash
curl -X PUT http://127.0.0.1:6333/collections/sdemo -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Euclid"},
       "strict_mode_config": {"enabled": true, "max_query_limit": 5}}'
curl -X PUT "http://127.0.0.1:6333/collections/sdemo/points?wait=true" -H 'Content-Type: application/json' \
  -d '{"points": [
    {"id": 1, "vector": [0.1, 0.2, 0.3, 0.4]}, {"id": 2, "vector": [0.2, 0.2, 0.3, 0.4]},
    {"id": 3, "vector": [0.3, 0.2, 0.3, 0.4]}, {"id": 4, "vector": [0.4, 0.2, 0.3, 0.4]},
    {"id": 5, "vector": [0.5, 0.2, 0.3, 0.4]}, {"id": 6, "vector": [0.6, 0.2, 0.3, 0.4]},
    {"id": 7, "vector": [0.7, 0.2, 0.3, 0.4]}, {"id": 8, "vector": [0.8, 0.2, 0.3, 0.4]},
    {"id": 9, "vector": [0.9, 0.2, 0.3, 0.4]}, {"id": 10, "vector": [1.0, 0.2, 0.3, 0.4]},
    {"id": 11, "vector": [1.1, 0.2, 0.3, 0.4]}, {"id": 12, "vector": [1.2, 0.2, 0.3, 0.4]}
  ]}'
```

2. Scroll with an omitted limit:

```bash
curl -s -X POST http://127.0.0.1:6333/collections/sdemo/points/scroll -H 'Content-Type: application/json' -d '{}'
# → 200, 10 points (exceeds max_query_limit=5)
```

3. Control — explicit limit above the cap is rejected:

```bash
curl -s -X POST http://127.0.0.1:6333/collections/sdemo/points/scroll -H 'Content-Type: application/json' \
  -d '{"limit": 6}'
# → 400 Limit exceeded 6 > 5 for "limit"
```

The data used to reproduce: any 12-point collection; the strict-mode config is the only unusual input.

## Expected Behavior

Either the omitted limit should be capped by `max_query_limit` (as the query family does, by materializing the default before validation), or the request should be rejected. The asymmetric enforcement undermines the guard's purpose: the most common usage — omitting `limit` — silently bypasses it.

## Possible Solution

Materialize the scroll default limit before the strict-mode validation (mirroring the query family's materialize-then-verify order), so the omitted limit meets the same cap as an explicit one.

## Context (Environment)

- Versions verified: v1.19.0 and v1.18.0, standalone.
- Impact: strict_mode's resource guard is ineffective for the default scroll path. A client that never sends `limit` (the common case) consistently gets pages larger than the configured bound, with no error or warning.

## Detailed Description

- The scroll path validates the raw `Option<usize>` first (`check_limit_opt` requires both sides to be `Some`, so `None` passes) and applies `unwrap_or(default)` only afterwards — the omitted limit never meets the cap.
- The query/search family materializes defaults before validation, which is why they cap correctly — the scroll path validates the raw `Option` and applies `unwrap_or(default)` only after the check.

## Possible Implementation

- Move the default-limit materialization for scroll before the strict-mode validation (aligning with the query family's order), so an omitted limit is capped identically to an explicit one.
