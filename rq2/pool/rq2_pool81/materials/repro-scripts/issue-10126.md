# TITLE: `count` `exact=false` on `geo_radius` degenerates: medium radii collapse to a fixed value, large radii return the collection total


## Current Behavior

`POST /collections/{c}/points/count` with `exact=false` on a `geo_radius` filter returns severely wrong counts:

- **Medium radii** collapse to a **fixed** estimated value regardless of the true count (two radii with true counts of 18 and 112 both return ~133)
- **Large radii** return the **total collection size** regardless of selectivity (true=503 → returns 1000)

`exact=true` is always correct. Worst observed error: **+639%** (true=18, returned=133). This makes approximate geo counts effectively unusable.

Not the `total/2` fallback (medium-radius value is a fixed sub-fraction like `total/8`, not `total/2`; large-radius returns `total`, not `total/2`).

The Qdrant OpenAPI specification ([v1.18.3 `openapi.json`](https://github.com/qdrant/qdrant/blob/v1.18.3/docs/redoc/v1.8.x/openapi.json)) defines:

> **`CountRequest.exact`**: "If `true`, count exact number of points. If `false`, count approximate number of points faster. **Approximate count might be unreliable during the indexing process.**"

> **`FieldCondition.geo_radius`**: "Check if geo point is within a given radius"

The +639% error occurs at **steady state**, outside the documented caveat. The documentation describes `geo_radius` as a boolean predicate ("check if geo point is within a given radius") — it does not suggest the approximate count would be meaningless.

## Steps to Reproduce

```python
import json, urllib.request, random, time

BASE = "http://127.0.0.1:6333"

def http(method, path, body=None):
    data = json.dumps(body).encode() if body is not None else None
    req = urllib.request.Request(BASE + path, data=data, method=method)
    if body:
        req.add_header("Content-Type", "application/json")
    with urllib.request.urlopen(req, timeout=20) as resp:
        return resp.status, json.loads(resp.read().decode())

http("DELETE", "/collections/c")
http("PUT", "/collections/c", {
    "vectors": {"size": 2, "distance": "Cosine"},
    "optimizer_config": {"indexing_threshold": 1}
})
random.seed(42)
pts = [{"id": i+1, "vector": [1, 0],
        "payload": {"loc": {"lat": random.uniform(-89, 89), "lon": random.uniform(-179, 179)}}}
       for i in range(1000)]
http("PUT", "/collections/c/points?wait=true", {"points": pts})
http("PUT", "/collections/c/index", {"field_name": "loc", "field_schema": "geo"})
time.sleep(3)

def count(flt, exact):
    _, r = http("POST", "/collections/c/points/count", {"exact": exact, "filter": flt})
    return r["result"]["count"]

def radius(r):
    flt = {"must":[{"key":"loc","geo_radius":{"center":{"lat":0,"lon":0},"radius":r}}]}
    return count(flt, True), count(flt, False)

for r in [500_000, 2_000_000, 5_000_000, 10_000_000, 20_000_000]:
    t, f = radius(r)
    err = (f - t) * 100 // t if t else 0
    print(f"radius={r//1000}km: exact={t:4d} approx={f:4d} ({err:+d}%)")
```

**Output:**
```
radius=500km:    exact=   2 approx=   4 (+100%)
radius=2000km:   exact=  18 approx= 133 (+639%)
radius=5000km:   exact= 112 approx= 133 (+18%)  ← SAME 133 as 2000km!
radius=10000km:  exact= 503 approx=1000 (+99%)  ← returns collection total
radius=20000km:  exact=1000 approx=1000 (OK)
```

Note: radii 2000km and 5000km both return ~133 despite very different true counts (18 vs 112) — the estimator has collapsed to a fixed value.

## Expected Behavior

Approximate geo_radius counts should track the actual selectivity of the radius, not collapse to a fixed sub-fraction or saturate to the collection total. If the geo index cannot provide a reasonable estimate, fall back to `exact=true`.

## Possible Solution

Fall back to `exact=true` for `geo_radius` filters when `exact=false`, since the geo index doesn't support efficient cardinality estimation for arbitrary circles.

## Context (Environment)

- Qdrant v1.18.3 (commit `db8fa43f`)
- Official Docker image (`qdrant/qdrant:v1.18.3`)
- Single node, default configuration

## Detailed Description

The geo-radius cardinality estimator appears to degenerate for non-trivial radii. At medium radii it locks to a fixed sub-fraction of the collection (roughly `total/8`), and at large radii it saturates to `total`. This suggests a bucketing/Layout-size assumption that stops matching the true spatial distribution at certain radius thresholds.

**Not a duplicate:** Not the `total/2` fallback (medium-radius value is a fixed sub-fraction, not half; large-radius returns total, not half).

## Possible Implementation

For `geo_radius` filters, route `exact=false` through `exact=true` (the geo index supports exact range queries). The performance cost is `O(log n)` per query, acceptable for count operations.
