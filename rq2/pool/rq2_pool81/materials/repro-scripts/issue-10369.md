# TITLE: `recommend` bypasses vector dimension validation for `negative` examples from `lookup_from`, returning silently wrong scores

## Current Behavior

`POST /collections/{c}/points/recommend` validates the vector dimension of **positive** examples resolved via `lookup_from` (returns 400 "Vector dimension error"), but the same dimension mismatch on **negative** examples is silently accepted with HTTP 200: the oversized negative vector is **truncated to the collection dimension by `zip`** and participates in scoring, producing scores that match the truncation prediction — a silently wrong result, not an error.

## Steps to Reproduce

Verified on **v1.18.0 and v1.19.0**; deterministic (two independent runs per version, identical scores).

1. Create a dim-4 main collection with two points:

```bash
curl -X PUT http://127.0.0.1:6333/collections/main -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Euclid"}}'
curl -X PUT "http://127.0.0.1:6333/collections/main/points?wait=true" -H 'Content-Type: application/json' \
  -d '{"points": [{"id": 1, "vector": [0.1, 0.2, 0.3, 0.4]}, {"id": 2, "vector": [0.4, 0.3, 0.2, 0.1]}]}'
```

2. Create a dim-8 lookup collection with one point:

```bash
curl -X PUT http://127.0.0.1:6333/collections/lookup8 -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 8, "distance": "Euclid"}}'
curl -X PUT "http://127.0.0.1:6333/collections/lookup8/points?wait=true" -H 'Content-Type: application/json' \
  -d '{"points": [{"id": 100, "vector": [0.9, 0, 0, 0, 0, 0, 0, 0]}]}'
```

3. Control case — positive resolved from the lookup collection (dim 8) is correctly rejected:

```bash
curl -X POST http://127.0.0.1:6333/collections/main/points/recommend -H 'Content-Type: application/json' \
  -d '{"positive": [100], "limit": 2, "lookup_from": {"collection": "lookup8"}}'
# → 400 "Vector dimension error: expected dim: 4, got 8"
```

4. Bug case — the same oversized vector used as a **negative** is accepted, and the returned scores match a dimension-truncated negative exactly:

```bash
curl -X POST http://127.0.0.1:6333/collections/main/points/recommend -H 'Content-Type: application/json' \
  -d '{"positive": [[0.1, 0.2, 0.3, 0.4]], "negative": [100], "limit": 3, "lookup_from": {"collection": "lookup8"}}'
# → 200 {"result":[{"id":1,"score":0.9643651},{"id":2,"score":1.3674794}],...}
```

The data used to reproduce: dim-4 main collection (any vectors), dim-8 lookup collection; the negative id refers to the 8-dim lookup point.

## Expected Behavior

The dimension constraint on `lookup_from`-resolved examples ("lookup_from collection must have the same vector size as the target collection") should hold for **both** positive and negative examples. Step 4 should fail with the same 400 dimension error as step 3 (as it does when negatives are routed through the searchable path under non-default recommend strategies).

## Possible Solution

Validate negative-example dimensions in `merge_positive_and_negative_avg` (`lib/collection/src/recommendations.rs`) before the `pos + pos - neg` combination, or replace the `.zip(negative.iter())` truncation with an explicit dimension assertion so the request fails with a 4xx instead of computing scores from a silently truncated vector.

## Context (Environment)

- Versions verified: v1.18.0 and v1.19.0, standalone, two independent runs per version with identical scores.
- Impact: clients receive HTTP 200 with scores computed from a silently altered query vector. The results are wrong in a way invisible at the protocol level — the caller believes the negative example was applied at full dimensionality.

## Detailed Description

Root cause (`lib/collection/src/recommendations.rs`):

- `merge_positive_and_negative_avg` combines `pos + pos - neg` via `.zip(negative.iter())` (L110-114), which silently drops the extra dimensions of an oversized negative.
- The dimension check exists only at the segment-query entry (`common/mod.rs`); negatives on the default `AverageVector` strategy are arithmetically absorbed into the merged search vector (`L377-382`) and never reach that check.

Proof that the returned scores are computed from a truncated vector — the recommend query is `q = 2·avg(positive) − avg(negative)`; with the negative silently truncated from 8-d to 4-d (`[0.9, 0, 0, 0]`), `q = [-0.7, 0.4, 0.6, 0.8]`:

| id | returned score | prediction from truncated q |
|----|----------------|------------------------------|
| 1  | 0.9643651      | √0.93 = 0.96436508… (Δ ≈ 2e-8) |
| 2  | 1.3674794      | √1.87 = 1.36747944…  |

Additional observation for v1.19.0: when `lookup_from` is set, inline **id** positives are also resolved against the lookup collection ("No point with id … found" if absent) — the reproduction above uses an inline vector positive to isolate the dimension bypass.

## Possible Implementation

- Assert `negative.iter().all(|n| n.len() == dim)` (or convert and check) in the merge path before arithmetic, returning a validation error naming the offending example.
- Alternatively, apply the same segment-entry dimension check to merged recommend vectors, so positives and negatives fail symmetrically.
