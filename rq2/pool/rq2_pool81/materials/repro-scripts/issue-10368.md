# TITLE: Snapshot recovery with `priority: "replica"` silently destroys existing data in standalone mode


## Current Behavior

`PUT /collections/{c}/snapshots/recover` with `"priority": "replica"` returns HTTP 200 and **destroys the live data**, replacing it with the snapshot content — the opposite of the documented meaning of `replica`.

The OpenAPI spec (v1.18.x / v1.19.0) defines:

> `SnapshotPriority` — `"replica"`: **Replica means - prefer existing data over the snapshot**

and the `priority` field:

> "the current state will be used as a source of truth"

The implementation's own doc comments agree (`lib/storage/src/content_manager/snapshots/snapshot_ops.rs`: "Replica — current state is the source of truth"). However, in standalone mode the priority branch is unreachable: `recover.rs` performs `RecoveryType::Full` — which **deletes local shard data before priority is ever consulted** — and the dispatch short-circuits to `activate` when `other_active_replicas` is empty. Even granting the cluster-scoped reading of the field description, the admissible behaviors would be {keep existing data, reject with 4xx, warn} — silently overwriting with 200 is none of them.

## Steps to Reproduce

Verified on **v1.18.0 and v1.19.0**, standalone, deterministic (two independent runs each).

1. Create a collection with 3 points:

```bash
curl -X PUT http://127.0.0.1:6333/collections/demo -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Euclid"}}'
curl -X PUT "http://127.0.0.1:6333/collections/demo/points?wait=true" -H 'Content-Type: application/json' \
  -d '{"points": [{"id": 1, "vector": [0.1, 0.2, 0.3, 0.4]}, {"id": 2, "vector": [0.2, 0.3, 0.4, 0.5]}, {"id": 3, "vector": [0.3, 0.4, 0.5, 0.6]}]}'
```

2. Create a snapshot:

```bash
curl -X POST "http://127.0.0.1:6333/collections/demo/snapshots?wait=true"
# → {"result":{"name":"demo-<peer>-<TS>.snapshot",...}}
```

3. Add a NEW live point (data that must survive a "prefer existing data" recovery):

```bash
curl -X PUT "http://127.0.0.1:6333/collections/demo/points?wait=true" -H 'Content-Type: application/json' \
  -d '{"points": [{"id": 50, "vector": [0.9, 0.9, 0.9, 0.9]}]}'
```

4. Recover with `priority: "replica"`:

```bash
curl -X PUT "http://127.0.0.1:6333/collections/demo/snapshots/recover?wait=true" -H 'Content-Type: application/json' \
  -d '{"location": "file:///qdrant/snapshots/demo/<SNAPSHOT_NAME>", "priority": "replica"}'
# → 200 {"result":true,...}
```

5. Observe that the live point is gone:

```bash
curl -X POST http://127.0.0.1:6333/collections/demo/points/count -H 'Content-Type: application/json' -d '{"exact": true}'
# → {"result":{"count":3}}   (id 50 silently destroyed)
```

The data used to reproduce: any 4-dim Euclid collection; the point added at step 3 is the one that disappears.

## Expected Behavior

With `priority: "replica"`, the existing live data must be preserved (per the enum description), **or** the request must be rejected with a 4xx explaining that the requested priority cannot be honored in this topology. Silent data replacement with 200 matches none of the documented semantics.

## Possible Solution

In `recover.rs`, when `other_active_replicas` is empty (standalone), a requested `Replica` priority currently cannot be honored — return a 4xx explaining this instead of running the destructive full recovery. Alternatively, honor the documented semantics by skipping data destruction when `priority == Replica`.

## Context (Environment)

- Versions verified: v1.18.0 and v1.19.0, standalone (single node, no consensus), deterministic on two independent runs per version.
- Impact: silent data loss on a code path that returns success. Users relying on `replica` as a safety guard during recovery lose post-snapshot writes without any signal.

## Detailed Description

Source walk (`lib/storage/src/content_manager/snapshots/recover.rs` unless noted):

1. `L273` — `priority.unwrap_or_default()` (default = Snapshot).
2. `L289-296` — `RecoveryType::Full` **destroys local shard data before priority is ever dispatched**.
3. `L344-368` — `if other_active_replicas.is_empty() { activate } else { match priority }` — in standalone the priority branch is structurally unreachable.
4. `L406-418` — the `Replica` arm is implemented as a cluster-only `request_shard_transfer` (`.unwrap()` assumes peers exist).

The openapi `SnapshotPriority` enum-level description ("Replica means - prefer existing data over the snapshot") carries no cluster qualifier, and the implementation's own doc comment (`snapshot_ops.rs`: "Replica — current state is the source of truth") states the same contract — so the standalone short-circuit contradicts both documented layers.

## Possible Implementation

- Option A (minimal): when `priority == Replica` and the topology cannot honor it (no other active replicas), reject with 4xx instead of proceeding with the destructive recovery.
- Option B (fuller): implement the documented replica semantics in standalone by skipping data destruction (the local shard *is* the surviving replica).

## Known limitation of this report

Cluster-topology behavior of the `Replica` branch was not exercised; this report covers standalone only.
