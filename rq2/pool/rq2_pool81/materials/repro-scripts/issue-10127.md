# TITLE:  `count` `exact=false` on `match_any` (multi-value) under-counts, increasingly with value count (independent-OR assumption)

## Current Behavior

`POST /collections/{c}/points/count` with `exact=false` on a `match_any` filter under-counts, and the error **grows with the number of values** in the `any` array. `exact=true` is correct. The **single-value** form is exact-correct on both paths, so the bug is the multi-value OR estimator.

Not the `total/2` fallback: the error is a function of the number of values, not collection size.

The Qdrant OpenAPI specification ([v1.18.3 `openapi.json`](https://github.com/qdrant/qdrant/blob/v1.18.3/docs/redoc/v1.8.x/openapi.json)) defines:

> **`CountRequest.exact`**: "If `false`, count approximate number of points faster. **Approximate count might be unreliable during the indexing process.**"

> **`MatchAny`**: "Exact match on **any** of the given values"

The under-count occurs at **steady state**. For a single keyword field, `match_any` values are **mutually exclusive** (a point has one value) — the true count is the sum of individual counts, but the estimator uses an independence assumption that caps below the true value.

## Steps to Reproduce

```python
import json, urllib.request, random, time

BASE = "http://127.0.0.1:6333"

def http(method, path, body=None):
    data = json.dumps(body).encode() if body is not None else None
    req = urllib.request.Request(BASE + path, data=data, method=method)
    if body:
        req.add_header("Content-Type", "application/json")
    with urllib.request.urlopen(req, timeout=20) as resp:
        return resp.status, json.loads(resp.read().decode())

http("DELETE", "/collections/c")
http("PUT", "/collections/c", {
    "vectors": {"size": 2, "distance": "Cosine"},
    "optimizer_config": {"indexing_threshold": 1}
})
random.seed(42)
kws = ["red", "blue", "green", "yellow", "purple"]
pts = [{"id": i+1, "vector": [1, 0], "payload": {"kw": random.choice(kws)}} for i in range(500)]
http("PUT", "/collections/c/points?wait=true", {"points": pts})
http("PUT", "/collections/c/index", {"field_name": "kw", "field_schema": "keyword"})
time.sleep(3)

def count(flt, exact):
    _, r = http("POST", "/collections/c/points/count", {"exact": exact, "filter": flt})
    return r["result"]["count"]

def any_of(vals):
    flt = {"must":[{"key":"kw","match":{"any":vals}}]}
    return count(flt, True), count(flt, False)

for n in range(1, 6):
    vals = kws[:n]
    t, f = any_of(vals)
    err = (f - t) * 100 // t if t else 0
    print(f"match_any {n} values {vals}: exact={t:3d} approx={f:3d} ({err:+d}%)")
```

**Output:**
```
match_any 1 values ['red']:                exact=107 approx=107 (  0%)  ← single = correct
match_any 2 values ['red','blue']:         exact=213 approx=189 (-11%)
match_any 3 values ['red','blue','green']: exact=284 approx=234 (-18%)
match_any 4 values:                        exact=391 approx=292 (-25%)
match_any 5 values:                        exact=500 approx=337 (-33%)
```

The under-count **grows** as more values are added, even though the true count approaches the collection total.

## Expected Behavior

For a single keyword field, `match_any` values are mutually exclusive (each point has exactly one value). The true count is `sum(count(kw=value_i))`. The estimator should use the sum (capped at collection total), not the independence-assumption OR formula.

## Possible Solution

For `match_any` on a single keyword field, use the sum `sum p_i` (cap at 1.0), which is exact for mutually exclusive values. Reserve the independence-OR formula for genuinely independent conditions.

## Context (Environment)

- Qdrant v1.18.3 (commit `db8fa43f`)
- Official Docker image (`qdrant/qdrant:v1.18.3`)
- Single node, default configuration

## Detailed Description

The cardinality estimator uses the independent-OR complement formula `1 - prod(1 - p_i)` for `match_any`, where `p_i = count(kw=value_i) / total`. This formula assumes statistical independence between the events "point has value_i". For mutually-exclusive values on a single keyword field, this formula is strictly below the true sum `sum p_i` and diverges as values are added.

For 5 uniform values (`p_i = 0.2` each), the formula gives `1 - (0.8)^5 ≈ 0.67`, so it can never reach the true 1.0 even when `match_any` covers the entire field.

**Not a duplicate:** Not the `total/2` fallback (error grows with value count, not collection size).

## Possible Implementation

For `match_any` on a single keyword-indexed field, use the sum of per-value cardinalities (cap at collection total). This is exact for mutually-exclusive values and degrades gracefully for genuinely independent multi-field conditions.
