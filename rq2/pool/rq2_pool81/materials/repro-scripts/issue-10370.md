# TITLE: `PATCH /collections/{c}` with `metadata: {}` does not remove metadata, contradicting the versioned API documentation


## Current Behavior

`PATCH /collections/{c}` with `{"metadata": {}}` returns 200 and **keeps all existing metadata keys**.

The versioned API documentation (v1.18.x, `update-collection`) states verbatim:

> `metadata` (map from string to any or any, optional) — Metadata to update for the collection. **If provided, this will merge with existing metadata. To remove metadata, set it to an empty object.**

This sentence is present in the live versioned page (archived copy: `v1-18-x_update-collection.md`).

## Steps to Reproduce

Verified on **v1.18.0 and v1.19.0**, standalone.

1. Create a collection with metadata:

```bash
curl -X PUT http://127.0.0.1:6333/collections/demo -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Euclid"}, "metadata": {"keep": "v1", "gone": "v2"}}'
```

2. Patch with an empty metadata object:

```bash
curl -X PATCH http://127.0.0.1:6333/collections/demo -H 'Content-Type: application/json' \
  -d '{"metadata": {}}'
# → 200
```

3. Read the collection back:

```bash
curl http://127.0.0.1:6333/collections/demo | python -m json.tool
# → metadata still contains {"keep": "v1", "gone": "v2"}
```

The data used to reproduce: any collection with non-empty metadata.

## Expected Behavior

Per the documented semantics, `metadata: {}` should remove the collection metadata (the stored metadata becomes empty).

## Possible Solution

Either implement the documented clearing semantics (treat `metadata: {}` as "remove metadata") in the PATCH handler, or update the versioned documentation to describe the implemented merge-only behavior and document the currently-undocumented per-key `null` removal as the clearing mechanism.

## Context (Environment)

- Versions verified: v1.18.0 and v1.19.0, standalone.
- Impact: users cannot clear collection metadata through the documented path. Notably, setting **per-key** `null` values *does* remove individual keys — an undocumented capability that *is* implemented — making the documented whole-object path and the implemented behavior inconsistent in both directions.

## Detailed Description

- The metadata update is merge-only (no clear branch in the update path) — consistent with the empty-object no-op but inconsistent with the documentation.
- This also deviates from RFC 7386 JSON Merge Patch semantics, where `{}` is a no-op — the versioned doc explicitly promises otherwise, so the documentation is the odd one out and either the doc or the behavior should change.
- Related observation: `metadata: null` is rejected; per-key `null` removal works but is undocumented.

## Possible Implementation

- Option A (behavior): special-case `metadata: {}` in the PATCH handler to clear the metadata, matching the documented sentence.
- Option B (docs): rewrite the versioned page to describe merge-only semantics and document per-key `null` removal as the clearing mechanism (the page currently omits it).
