# TITLE: `count` `exact=false` on `is_empty` under-counts ~35% consistently; `is_null` on the same field is correct

## Current Behavior

`POST /collections/{c}/points/count` with `exact=false` on an `is_empty` condition over a keyword-indexed field returns a **consistent ~-35% under-count** across collection sizes. `exact=true` returns the correct count. This occurs at **steady state** (after indexing completes), outside the documented "unreliable during indexing" window.

On the **same collection**, the analogous `is_null` condition returns identical (correct) counts on both `exact=true` and `exact=false` paths. This isolates the bug to the `is_empty` condition's cardinality estimation path, not the field, the index, or the general count estimator.

The error is a **stable percentage** (~-35%), not the `total/2` fallback — verified across collection sizes 200, 500, and 1000.

The Qdrant OpenAPI specification (v1.18.3, [`openapi.json`](https://github.com/qdrant/qdrant/blob/v1.18.3/docs/redoc/v1.8.x/openapi.json)) defines `exact` as:

> "If `true`, count exact number of points. If `false`, count approximate number of points faster. **Approximate count might be unreliable during the indexing process.** Default: `true`"

And `IsEmptyCondition` as:

> "Select points with **empty payload** for a specified field"

The ~-35% under-count occurs at steady state (after indexing completes), which is outside the documented unreliability window. The documentation does not state that `is_empty` approximate counts would be systematically biased where `is_null` on the same field is exact.

## Steps to Reproduce

```python
import json, urllib.request, time

BASE = "http://127.0.0.1:6333"

def http(method, path, body=None):
    data = json.dumps(body).encode() if body is not None else None
    req = urllib.request.Request(BASE + path, data=data, method=method)
    if body:
        req.add_header("Content-Type", "application/json")
    with urllib.request.urlopen(req, timeout=20) as resp:
        return resp.status, json.loads(resp.read().decode())

def run(size):
    http("DELETE", "/collections/c")
    http("PUT", "/collections/c", {
        "vectors": {"size": 2, "distance": "Cosine"},
        "optimizer_config": {"indexing_threshold": 1}
    })
    # 80% of points carry "kw": "red", 20% are MISSING kw
    # is_empty should match the 20% missing kw
    pts = []
    for i in range(size):
        p = {"id": i + 1, "vector": [1, 0]}
        if i % 5 != 0:
            p["payload"] = {"kw": "red"}
        pts.append(p)
    http("PUT", "/collections/c/points?wait=true", {"points": pts})
    http("PUT", "/collections/c/index", {"field_name": "kw", "field_schema": "keyword"})
    time.sleep(3)

    def count(flt, exact):
        _, r = http("POST", "/collections/c/points/count", {
            "exact": exact,
            "filter": {"must": [flt]}
        })
        return r["result"]["count"]

    ie_true  = count({"is_empty": {"key": "kw"}}, True)
    ie_false = count({"is_empty": {"key": "kw"}}, False)
    in_true  = count({"is_null": {"key": "kw"}}, True)
    in_false = count({"is_null": {"key": "kw"}}, False)
    err = (ie_false - ie_true) * 100 // ie_true if ie_true else 0
    print(f"size={size}: is_empty exact={ie_true} approx={ie_false} ({err}%) | "
          f"is_null exact={in_true} approx={in_false}")

run(200)
run(500)
run(1000)
```

**Output:**

```
size=200:  is_empty exact=40  approx=25  (-37%) | is_null exact=0  approx=0
size=500:  is_empty exact=100 approx=65  (-35%) | is_null exact=0  approx=0
size=1000: is_empty exact=200 approx=131 (-34%) | is_null exact=0  approx=0
```

**Control experiment (is_null is correct on the same collection):**

If you additionally seed some points with `"kw": null`, `is_null` returns a non-zero but exact-correct count on both paths, while `is_empty` continues to under-count by ~35%:

```python
# After seeding kw: null on some points:
is_null  exact=50  approx=50   ← correct on both paths
is_empty exact=200 approx=131  ← still -34% on approx path
```

## Expected Behavior

`is_empty` `exact=false` should return a count consistent with `exact=true` (as `is_null` does on the same collection), **at steady state (after indexing completes)**. The documentation states approximate counts "might be unreliable during the indexing process" — at steady state, the ~-35% systematic under-count falls outside this documented caveat.

At minimum, the error should not be a systematic ~-35% under-count. If the cardinality estimator cannot provide a reasonable approximation for `is_empty`, it should fall back to `exact=true` for this condition.

## Possible Solution

Route `is_empty` `exact=false` through the same cardinality source as `is_null` (which is exact via the null-index), or fall back to `exact=true` when the estimator cannot achieve reasonable accuracy for `is_empty`.

## Context (Environment)

- Qdrant v1.18.3 (commit `db8fa43f`)
- Official Docker image (`qdrant/qdrant:v1.18.3`)
- Single node, default configuration
- Reproduced on 3 collection sizes (200, 500, 1000 points) with consistent error percentage

## Detailed Description

The `count` API's `exact=false` path uses a cardinality estimator for performance. For `is_empty`, this estimator appears to take a different code path than `is_null`, even though both conditions query the same underlying "field is absent/null" semantics on a keyword-indexed field.

The `is_null` path goes through the null-index and returns an exact count even with `exact=false`. The `is_empty` path appears to use a histogram or sampling estimator that systematically under-counts the set of points missing the field by ~35%.

This is not a correctness issue for `exact=true` (which always returns the correct count). However, users relying on `exact=false` for performance (e.g., dashboards, monitoring) will see consistently wrong counts for `is_empty` conditions.

**Not a duplicate of existing issues:**
- Not #8723 / #8734: those are about `is_empty` **visibility** of cleared fields after payload-index **rebuild**. This issue is a **steady-state** cardinality under-count, verified at rest after index creation with no rebuild involved.
- Not #10096 / #10101: those are `IsNull` indexed-vs-unindexed behavior and `IsNull`-on-arrays. This is `is_empty`, and `is_null` is shown here as a correct control on the same collection.
- Not the `total/2` fallback: the error is a stable percentage (~-35%), not half the collection size. Verified by varying collection sizes.

## Possible Implementation

Route `is_empty` `exact=false` through the same cardinality source as `is_null` (which is exact via the null-index), or fall back to `exact=true` for `is_empty` when the indexed estimate cannot be made exact.
