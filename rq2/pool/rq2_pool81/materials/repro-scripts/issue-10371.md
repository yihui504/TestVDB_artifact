# TITLE: `query/groups` without a query returns nondeterministic group members across identical requests (schema documents "ordered by their IDs")


## Current Behavior

On a frozen collection, sending the **same** `POST /collections/{c}/points/query/groups` request repeatedly (no `query`, no `prefetch`) returns different group **memberships** each time when the number of tied points exceeds `group_size`. Across 10 consecutive identical requests we observed 8 distinct member-set/order signatures.

The `QueryGroupsRequest.query` schema states:

> "Query to perform. **If missing without prefetches, returns points ordered by their IDs**"

The flat `/points/query` endpoint honors this — returning points in ascending id order, deterministically. The groups endpoint does not: intra-group order is arbitrary and `group_size` truncation therefore selects an arbitrary subset of the tied points on every call.

## Steps to Reproduce

Verified on **v1.19.0** (same on v1.18.0); deterministic collection state, nondeterministic member selection across re-creation.

1. Create a collection with 8 **identical** vectors and alternating group labels (so every point ties at the same score):

```bash
curl -X PUT http://127.0.0.1:6333/collections/gdemo -H 'Content-Type: application/json' \
  -d '{"vectors": {"size": 4, "distance": "Euclid"}}'
curl -X PUT "http://127.0.0.1:6333/collections/gdemo/points?wait=true" -H 'Content-Type: application/json' \
  -d '{"points": [
    {"id": 1, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "a"}},
    {"id": 2, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "b"}},
    {"id": 3, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "a"}},
    {"id": 4, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "b"}},
    {"id": 5, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "a"}},
    {"id": 6, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "b"}},
    {"id": 7, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "a"}},
    {"id": 8, "vector": [0.1, 0.2, 0.3, 0.4], "payload": {"grp": "b"}}
  ]}'
```

2. Send the same groups request 10 times and compare:

```bash
for i in $(seq 1 10); do
  curl -s -X POST http://127.0.0.1:6333/collections/gdemo/points/query/groups \
    -H 'Content-Type: application/json' \
    -d '{"group_by": "grp", "limit": 2, "group_size": 3}' \
    | jq -c '[.result.groups[] | {grp: .hits[0].payload.grp, ids: [.hits[].id]}]'
done
# → 8 distinct signatures observed in 10 identical calls
```

The data used to reproduce: 8 points sharing one vector, two group labels; `group_size` smaller than the tie pool makes the truncation face visible.

## Expected Behavior

Per the documented fallback, results should be stably ordered by id — and therefore a deterministic member subset when `group_size` truncates — matching the flat endpoint's behavior.

## Possible Solution

Add an id tie-break to the group aggregation ordering (e.g., order hits by `(score, id)`), or collect group members deterministically (sort by id before truncation), so that identical requests on a frozen collection return identical groups.

## Context (Environment)

- Versions verified: v1.19.0 and v1.18.0, standalone.
- Impact: pagination/truncation over tied candidates is nondeterministic across identical requests — the same logical query returns different group members between calls, breaking reproducibility for downstream consumers (a client paging through results sees members appear and disappear).

## Detailed Description

- Correctness is preserved: every returned point is a genuine nearest neighbor (all tied). The issue is determinism/member selection, not accuracy.
- Root cause: intra-group scoring produces all-equal scores (constant), `ScoredPoint` ordering compares score only (no id tie-break), and the group aggregation's hash-map drain order is arbitrary — tie-breaking falls to insertion order, which varies with the collection's internal layout.
- The flat `/points/query` endpoint, on the same frozen collection and same tie conditions, returns a deterministic id-ordered result — a useful in-tree reference for the fix.

## Possible Implementation

- Apply a `(score, id)` comparison in the group hit ordering (mirroring any flat-endpoint ordering guarantees), so `group_size` truncation and pagination become deterministic.
